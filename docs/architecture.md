# Architecture

The GameCube is the SI host. It initiates every JoyBus operation on port 2. The GBA is the peripheral. The GC asks for data with WRITE, then drains the GBA's response with READ. The console and test runner live above the transport.

```text
GameCube bench / GX     GBA client / fixture
        session request/response dispatcher
            protocol/wire.c on both systems
     libogc SI_Transfer <-> LinkCube IRQ/queues
```

On GBA, the serial IRQ handles the LinkCube registers and queues. The main loop performs framing, CRC, display and fixture generation. On GC, the SI completion callback records status only. The GC transfer driver checks the completion and the READ status byte. If JOYSTAT.TRANS is clear, the returned register value can be stale. Such a READ is discarded and bounded polling continues. Accepting those words caused duplicate magic words in bulk frames during development.

The codec has no SDK headers, game structs or transport timing. Future transports can carry its logical frames without adopting the JoyBus READ/WRITE or idle-word behavior. Both transport and session state are in RAM. A JoyBus reset clears the pending request and bulk transaction; a new session starts with HELLO. Bulk data is generated by offset, with no 64 KiB allocation on GBA. The GC verifies the entire received sprite before conversion from tiled 4bpp/BGR555 to tiled RGB5A3 for GX.

LinkCube is pinned and vendored without source changes. Both binaries are homebrew and make no use of existing Pokémon ROMs or saves.
